## 一、现状问题诊断

### 1.1 五模块职责重叠

| 模块 | 路径 | 实际职责 | 问题 |
|---|---|---|---|
| **本地资料** Knowledge | `/knowledge` | 上传 → 解析 → 脱敏 → 筛选 → 供 AI 检索 | 和 Wiki、Cases 高度重叠 |
| **文档智能** Desensitize | `/desensitize` | 独立脱敏工具台 + 解析引擎设置 | 命名混乱，和 Knowledge 的解析/脱敏重复 |
| **Wiki** | `/wiki` | 从文档自动生成知识页面 | 本质是 Knowledge 的上层应用，不应平级 |
| **案件卷宗** Cases | `/cases` | 扫描外部文件夹 → 批量解析 | 和 Knowledge 同一流程，只是多了案件分组 |
| **文档工坊** DocForge | — | 代码中的命名别名 | 三名并存（desensitize/docforge/文档智能） |

### 1.2 核心矛盾

四个模块都在处理同一件事——**"文档从哪里来 → 怎么读 → 怎么脱敏 → 怎么给 AI 用"**，只是各自做了其中一段，用户需要跨页面操作才能完成完整流程。

### 1.3 安全设计缺失

- 脱敏流程没有分阶段安全策略
- 用户无法选择各阶段使用本地还是云端引擎
- 没有 AI 辅助验证的明确设计
- 跨文档代号一致性无保障
- 反请求中的相对命名问题未处理

## 二、设计原则

1. **案件为中心** — 一切围绕案件展开，用户来了先开案件
2. **流水线为手段** — 文档加工是可视化的流水线，状态一目了然
3. **安全为底线** — 云端 AI 只接触已脱敏文本，原始版默认不进 AI
4. **C 端友好** — 菜单精简、操作集中、流程不跨页面
5. **分层兼容** — 普通办公电脑到高配服务器都能用

## 三、模块重构方案

### 3.1 重构总览

```
现有（5 个独立模块）             →    重构后（2 个入口）
┌──────────┐ ┌──────────┐              ┌──────────────┐
│ Knowledge │ │ Desensitize│              │  案件中心     │  ← 顶层组织单元
├──────────┤ ├──────────┤              │  (仪表盘)     │
│  Cases   │ │   Wiki   │              ├──────────────┤
└──────────┘ └──────────┘              │  文档中心     │  ← 合并全部文档功能
                                       │  (Tab切换)    │
                                       └──────────────┘
```

### 3.2 案件中心（Case Center）

**定位**：顶层组织单元，一切围绕案件展开。

每个案件是一个完整工作区，包含：
- 案件基本信息（案号、当事人、仲裁机构、案件类型、状态）
- 关联材料概览（从文档中心引用，按案件过滤）
- 实体注册表（代号映射，此案件专属）
- AI 对话记录（针对此案件的 AI 交互）
- 文书草稿（裁决书草稿、调解方案等）
- 时间线（程序节点：立案、组庭、开庭、裁决）
- 脱敏状态总览（哪些材料已脱敏、哪些待处理）

用户打开案件中心，第一眼看到的是"这个案件到哪了、还差什么"的仪表盘视图。

**实施分阶段**：
- Phase 1：案件作为材料的**分组维度**（类似文件夹），仪表盘显示该案件的材料列表和状态
- Phase 2：案件上下文渗透到 AI 对话（选择案件 → 自动加载该案件材料作为上下文）

### 3.3 文档中心（Doc Center）

**定位**：合并 Knowledge + Desensitize + Cases + Wiki，通过内部 Tab 串联完整流水线。

```
文档中心 /documents
├── Tab 1: 材料库
│   ├── 左侧：分类树（案件分组 + 自定义分类 + 标签）
│   ├── 右侧：文档列表（卡片/表格双视图）
│   │   └── 每个文档卡片：
│   │       · 文件名 + 类型图标
│   │       · 处理状态流水线：上传 → 解析 → 脱敏 → 验证
│   │       · 当前引擎标签（Tesseract / MinerU☁️ / 正则+AI☁️）
│   │       · 安全等级图标（🔒/⚖️/☁️）
│   │       · 操作：解析 / 脱敏 / 查看 / 删除
│   └── 顶部工具栏：上传 / 扫描文件夹 / 批量脱敏 / 引擎设置
│
├── Tab 2: 脱敏工作台
│   · 即时脱敏（粘贴文本 → 脱敏，不入库的快速操作）
│   · 从材料库选材 → 批量脱敏
│   · 脱敏结果对比视图（原版 vs 脱敏版 diff）
│   · 代号映射表查看与编辑
│
└── Tab 3: 引擎设置
    · 解析引擎配置（MinerU / Tesseract / MarkItDown）
    · 脱敏规则管理（正则规则增删改）
    · AI 验证配置（本地/云端模型选择）
    · 代号策略配置（全局/案件级）
    · 安全等级默认值设置
```

### 3.4 知识库（Knowledge）— 独立菜单项

**定位**：跨案件的参考知识，不绑定具体案件，不含 PII，独立于文档中心。

**为什么独立**：知识库的使用场景与文档中心不同——用户在文档中心做的是「加工材料」，在知识库做的是「查阅参考知识」。将两者混在一个 Tab 里会让用户困惑。知识库是 AI 对话和模拟仲裁时的高频引用来源，需要快速独立访问。

知识库内容：
- 法律法规摘要（用户上传或系统预置）
- 先例案例要点（用户整理或 AI 提取）
- 仲裁规则与程序指引
- 用户笔记与经验总结
- 模板文书
- AI 生成的知识卡片（从案件脱敏材料中提取的可复用知识点）

**与文档中心的协同**：文档中心脱敏完成后，用户可将有价值的知识点「提取到知识库」，形成从材料到知识的单向流动（详见第十节）。

### 3.5 命名统一

| 旧名称 | 新名称 | 理由 |
|---|---|---|
| `desensitize` (路由/API) | `documents` | 不再以脱敏命名整个模块 |
| `docforge` (代码别名) | 废弃 | 三名并存问题 |
| "文档智能" (菜单) | **「文档中心」** | C 端友好，涵盖全流程 |
| "本地资料" (菜单) | 合并进文档中心 | 消除重叠 |
| "案件卷宗" (菜单) | **「案件中心」** | 从空壳升级为工作台 |
| "Wiki" (菜单) | **「知识库」** | 独立菜单，定位为跨案件参考知识 |

## 五、文档处理流水线

每个文档经过五个阶段，每阶段可选引擎，状态全程可视：

```
上传文件
  │
  ▼
┌─────────────────────────────────────────┐
│ Stage 1: 导入与预处理                     │
│ · 格式检测与标准化                        │
│ · 图片质量检查                            │
│ · 页面分割                                │
│ 引擎：本地（免费）或云端 OCR API（付费）    │
└─────────────────────────────────────────┘
  │
  ▼
┌─────────────────────────────────────────┐
│ Stage 2: 解析与结构化                     │
│ · OCR 识别（如需）                        │
│ · 版面分析（标题/段落/表格/签章）           │
│ · 文本提取与结构化                        │
│ · 元数据提取（日期/类型/当事人线索）         │
│ 引擎：见第七节「解析引擎分层」              │
└─────────────────────────────────────────┘
  │ 产出：_parsed/{doc_id}.md
  ▼
┌─────────────────────────────────────────┐
│ Stage 3: 实体识别与脱敏                   │
│ · 第一轮：本地规则匹配（正则+词典）         │
│   - 16+ 内置规则：身份证/手机/银行卡/地址   │
│     /人名/案号/邮箱/公司名/车牌/护照等      │
│   - 本地运行，零数据外泄                   │
│ · 第二轮（可选）：AI 增强识别              │
│   - 检测规则遗漏的上下文敏感信息            │
│   - 本地 AI（需 GPU）或云端 AI（精度高）    │
│ · 代号替换：根据案件实体注册表统一替换       │
│ 引擎：本地正则（必选）+ AI增强（可选）      │
└─────────────────────────────────────────┘
  │ 产出：_desensitized/{doc_id}.md + backfill_map
  ▼
┌─────────────────────────────────────────┐
│ Stage 4: AI 辅助验证                     │
│ · 检查遗漏的 PII（上下文可推断的信息）      │
│ · 检查过度脱敏（误伤）                     │
│ · 输出验证报告                            │
│ 引擎：跳过 / 本地 AI / 云端 AI            │
│ ⚠️ 此阶段处理的是已脱敏文档，送云端风险低   │
└─────────────────────────────────────────┘
  │ 产出：validation_report/{doc_id}.json
  ▼
┌─────────────────────────────────────────┐
│ Stage 5: 代号回填与一致性校验              │
│ · 跨文档实体一致性检查                    │
│ · 相对命名冲突检测（反请求场景）            │
│ · 生成最终脱敏版，标记为"已验证"            │
│ · 更新案件实体注册表                       │
│ 引擎：完全本地                            │
└─────────────────────────────────────────┘
```

### 5.1 流水线状态机

```
 States:
   uploaded → parsing → parsed → desensitizing → desensitized
                                       ↓
                                  validating → validated → ready
                                       ↓
                                  (failed) ← 任何阶段失败
```

每个文档在 UI 上显示流水线进度条：`上传 ✓ → 解析 ✓ → 脱敏 ○ → 验证 ○`

## 六、安全架构

### 6.1 三档安全级别

| 安全档 | 代号 | 解析引擎 | 脱敏引擎 | AI验证 | 适用场景 | 数据外泄风险 |
|---|---|---|---|---|---|---|
| **全本地** | 🔒 T1 | 本地 OCR | 本地正则 + 本地 AI | 本地 AI / 人工 | 涉密案件 | 零 |
| **标准安全** | ⚖️ T2（默认） | 本地优先，大文档可选云端 | 本地正则 + 云端 AI 补漏 | 云端 AI（脱敏版） | 常规商事仲裁 | 低 |
| **效率优先** | ☁️ T3 | 云端 OCR | 本地正则（必选）+ 云端 AI | 云端 AI | 公开案件 | 中 |

### 6.2 核心安全原则

**红线**：云端 AI 只接触已脱敏文本，不接触原始文档。

- Stage 3 第二轮 AI 增强：先本地正则脱敏完成，再送 AI 补漏 → AI 看到的是半脱敏文本
- Stage 4 AI 验证：只送脱敏版 → AI 看到的是已脱敏文本
- Stage 5 代号回填：完全本地，真实姓名不出本机

**T3 的特殊处理**：T3 的"效率优先"体现在 OCR 解析环节允许上传原始扫描件到云端 OCR，但脱敏阶段仍然先走本地正则，云端 AI 只做正则后的补漏。

### 6.3 引擎选择矩阵

| 阶段 | 本地方案 | 云端方案 | 默认（T2） |
|---|---|---|---|
| OCR 解析 | Tesseract / PaddleOCR / MinerU本地 | MinerU 云 API | 本地优先，大文档选云端 |
| 结构化 | MarkItDown / PyMuPDF | MinerU 云 API | 本地 |
| PII 检测（规则） | 正则 + 词典（必选） | — | 本地（所有级别） |
| PII 检测（AI） | 本地 NLP 模型 | 云端 AI API | 云端（仅文本） |
| AI 验证 | 本地模型 | 云端模型 | 云端（脱敏版） |
| 代号回填 | 本地规则 + 词典 | — | 本地（所有级别） |

### 6.4 设备适配

| 设备类型 | 推荐级别 | 解析 | 脱敏 | AI验证 |
|---|---|---|---|---|
| 普通办公电脑（无 GPU, 4-8GB） | T2 | PyMuPDF+MarkItDown（数字文档）/ MinerU云API（扫描件） | 本地正则 + 云端AI补漏 | 云端AI |
| 高配置电脑（有 GPU, 16GB+） | T1 或 T2 | MinerU 本地部署 | 本地正则 + 本地AI | 本地AI |
| 云端服务器（Docker） | T1 或 T2 | 服务器本地或云端 API | 本地正则 + 服务器AI | 服务器AI |

## 七、解析引擎分层

### 7.1 三层架构

```
Tier 1 — MinerU（最高精度，需配置）
  ├─ 云端 API（mineru.net）
  │   · 零安装，需 API Key
  │   · 支持 PDF/图片/Office 全格式
  │   · 表格/公式/版面识别最佳
  │   · 数据上传到第三方服务器
  │
  └─ 本地部署（.mineru-venv）
      · 需 GPU 或高性能 CPU
      · 完全离线运行
      · 自动检测 venv 并启动
      · 数据不出本机

Tier 2 — Tesseract + PyMuPDF（轻量本地，零依赖）
  ├─ PyMuPDF 检测 PDF 是否有文字层
  │   · 有文字层 → 直接提取（极速）
  │   · 无文字层 → 交给 Tesseract OCR
  │
  └─ Tesseract OCR
      · 需安装 Tesseract + Poppler
      · 支持 chi_sim + eng
      · 精度中等，扫描件可用
      · 完全离线

Tier 3 — MarkItDown（兜底，纯文本提取）
  · 处理 Office/HTML/Markdown/TXT
  · 无 OCR 能力
  · 所有环境可用
```

### 7.2 自动路由逻辑（parse_mode: auto）

```
1. 检测文件类型
2. PDF → 先查文字层（PyMuPDF）
   · 有文字层 → MarkItDown 提取（极速）
   · 无文字层 → 按引擎优先级 OCR
3. 图片 → 按引擎优先级 OCR（MinerU > Tesseract）
4. Office/TXT → MarkItDown 直接提取
5. MinerU 失败 → 降级到 Tesseract → 降级到 MarkItDown
```

### 7.3 引擎优先级配置

用户可在引擎设置中拖拽排序：

```
引擎优先级（自动模式）：
  1. [MinerU本地 ▼]  ← 优先尝试
  2. [MinerU云端 ▼]  ← 本地不可用时
  3. [Tesseract  ▼]  ← MinerU 失败时
  4. [MarkItDown ▼]  ← 兜底
```

### 7.4 解析模式

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `auto` | 按优先级自动选择，失败自动降级 | 默认 |
| `local_only` | 仅使用本地引擎（Tesseract + MarkItDown + MinerU本地） | 涉密案件 T1 |
| `cloud_ocr` | 强制使用云端 MinerU | 效率优先 T3 |

## 八、脱敏引擎与代号系统

### 8.1 双轮脱敏

**第一轮：本地规则匹配（必选，所有级别）**

16+ 内置正则规则：
- 身份证号、手机号、银行卡号、邮箱
- 详细地址（精确到门牌号）
- 人名（上下文标注：原告/被告/申请人/被申请人/代理人...）
- 案号（民事/仲裁，含地域标识）
- 公司名、车牌号、护照号、统一社会信用代码、税号

特点：本地运行，零数据外泄，速度快，覆盖模式固定的 PII。

**第二轮：AI 增强识别（可选）**

- 检测规则遗漏的上下文敏感信息
- 职务+年龄+性别组合可定位个人的描述
- 隐含的身份线索
- 引擎：本地 AI（需 GPU）或云端 AI（精度高，仅文本上传）

### 8.2 案件实体注册表

每个案件维护一个实体注册表：

```python
class Entity:
    canonical_id: str          # "E001"
    code_name: str             # "当事人一"（脱敏文档中使用）
    entity_type: str           # natural_person / legal_entity / other
    aliases_desensitized: list # ["申请人", "反请求被申请人", "张某"]
                               # ↑ 不含真实姓名，可明文存储
    real_name_encrypted: str   # AES加密，仅回填时解密
    role_contexts: dict        # {"本请求": "申请人", "反请求": "被申请人"}
    documents: list[str]       # 出现在哪些文档中
    confidence: float          # 匹配置信度
    status: str                # confirmed / pending / auto_merged
```

### 8.3 跨文档代号一致性流程

当新文档进入脱敏流程时：

```
第一步：PII 提取
  从当前文档中识别所有实体及其称呼形式

第二步：实体匹配（三级策略）
  · 精确匹配（置信度 > 90%）：姓名/证件号完全一致 → 自动合并
  · 模糊匹配（置信度 70-90%）：称呼不同但指向同一人 → 标记"待确认"
  · AI 辅助匹配（置信度 < 70%）：用 AI 判断是否同一实体 → 用户确认

  ⚠️ 匹配不阻塞流程，所有"待确认"项在 Stage 5 统一弹出确认面板

第三步：代号替换
  用注册表中的标准代号替换所有称呼形式
  "张某某" → "当事人一"
  "申请人" → "当事人一"（在本请求语境下）

第四步：注册表更新
  新发现的称呼形式加入 aliases 列表
```

### 8.4 相对命名处理（核心设计）

**设计原则：代号脱离角色，角色作为属性**

脱敏时统一使用中性代号（当事人一、当事人二、当事人三...），角色信息保留为实体属性而非代号本身。

**示例**：

| 场景 | 原文 | 脱敏后 |
|---|---|---|
| 本请求 | "申请人张某某请求被申请人 B 公司支付违约金" | "当事人一（本请求申请人）请求当事人二（本请求被申请人）支付违约金" |
| 反请求 | "反请求申请人 B 公司主张反请求被申请人 A 公司承担律师费" | "当事人二（反请求申请人）主张当事人一（反请求被申请人）承担律师费" |
| 笔录 | "张总说..." | "当事人一说..." |

代号（当事人一、当事人二）全局不变，角色标注随语境变化。用户和 AI 都能清晰追踪。

### 8.5 AI 辅助实体匹配

对于称呼差异大的情况（如"王总"和"法定代表人王某"）：
1. 将上下文片段（脱敏后）送入 AI 模型
2. AI 判断是否指同一人，返回置信度
3. 置信度 > 90% 自动合并，70-90% 待确认，< 70% 保留独立
4. T2 级别时可安全使用云端 AI（只送上下文片段，不含完整 PII）

## 九、双版本管理与 AI 材料选择器

### 9.1 双版本架构

每个文档维护两个版本：

| 版本 | 存储路径 | 可见性 | AI 可用 | 用途 |
|---|---|---|---|---|
| **原始版** | `files/{doc_id}.{ext}` | 仅授权用户 | ❌ 默认禁止 | 人工审阅、法律存档、文书回填 |
| **脱敏版** | `_desensitized/{doc_id}.md` | 授权用户 | ✅ 默认来源 | AI 分析、知识提取、检索索引 |

**切换与对照**：
- 材料库界面提供"原版 / 脱敏版"切换按钮
- diff 对比视图：高亮显示被脱敏的部分
- diff 仅在正则脱敏阶段提供（字符级替换可 diff），AI 增强阶段用"新增脱敏项列表"替代

### 9.2 原始版访问权限（三级）

| 权限级 | 行为 | 场景 |
|---|---|---|
| 默认禁止 | 原始版不可选入 AI 上下文 | 日常分析、检索 |
| 案件授权 | 案件管理员可临时授权 | 文书生成阶段 |
| 回填模式 | AI 输出脱敏版草稿 → 系统根据注册表自动回填真实信息 | 最终文书生成 |

**回填模式是最安全的文书生成方式**：AI 始终只处理脱敏文本，系统根据实体注册表自动将 AI 输出中的代号替换回真实姓名。AI 永远不接触 PII，但用户最终拿到含真实信息的文书。

### 9.3 AI 材料选择器

在对话/模拟仲裁中使用文档时，弹出材料选择器：

```
┌─────────── 选择材料 ───────────────┐
│ 🔍 搜索...                          │
│                                     │
│ 📁 仲裁案件-张某买卖合同纠纷         │
│   ☑ 仲裁申请书.md     [⚖️ 脱敏版 ▼] │
│   ☑ 答辩状.md         [⚖️ 脱敏版 ▼] │
│   ☐ 笔录-第一次.md    [⚖️ 脱敏版 ▼] │
│   ☑ 鉴定报告.pdf      [⚖️ 脱敏版 ▼] │
│                                     │
│ 📁 参考知识                          │
│   ☐ 合同法要点.md     [✓ 可用]      │
│   ☐ 先例案例集.md     [✓ 可用]      │
│                                     │
│ ────────────────────────────────    │
│ 已选 3 份材料 (脱敏版)               │
│ [确认使用]                          │
└─────────────────────────────────────┘
```

**选择维度**：
- 按案件（选择当前案件或关联案件）
- 按文档类型（申请书/答辩书/笔录/证据/法律依据）
- 按脱敏状态（已验证/已脱敏/全部）
- 按文档个体（勾选/取消勾选）
- AI 推荐（基于当前对话上下文自动推荐）

**默认行为**：
- 默认只选择已验证脱敏版
- 未验证的脱敏版可选但提示风险
- 原始版系统级禁止（除非管理员授权或回填模式）

## 十、知识库设计

### 10.1 定位

知识库是跨案件的参考知识，不绑定具体案件，不含 PII。

**与材料库的根本区别**：
- 材料库：案件文档（绑案件，含 PII，双版本）
- 知识库：参考知识（跨案件，不含 PII，单版本）

### 10.2 知识库内容

- 法律法规摘要（用户上传或系统预置）
- 先例案例要点（用户整理或 AI 提取）
- 仲裁规则与程序指引
- 用户笔记与经验总结
- 模板文书
- AI 生成的知识卡片（从案件脱敏材料中提取）

### 10.3 从材料到知识的单向流动

```
案件 A 脱敏材料 → AI 提取知识卡片 → 存入知识库 → 案件 B 可引用
                    ↑                              ↓
              AI 只输入脱敏版              知识卡片不含 PII
```

**安全要点**：
- AI 生成知识卡片时只输入脱敏版材料
- 生成后自动扫描卡片内容，检查 PII 残留
- 通过检查后才存入知识库

### 10.4 Wiki 功能整合

原 Wiki 的 `ingest` 功能整合为知识库的"生成知识卡片"：
- 从已脱敏文档中自动提炼概念页
- 生成案件对比分析
- 生成法律知识问答
- 全部基于脱敏版文档生成（安全）

## 十一、部署兼容性

### 11.1 本地桌面部署（Tauri 应用）

| 环节 | 方案 |
|---|---|
| 文档存储 | 本地文件系统 |
| OCR | 本地 Tesseract / PaddleOCR 或云端 MinerU API |
| AI 模型 | 本地 Ollama / llama.cpp 或云端 API |
| 检索 | 本地 SQLite / Whoosh 索引 |
| 实体注册表 | 本地加密存储（AES） |

新用户默认 T2 级别，第一次使用时引导配置。

### 11.2 云端部署（Docker）

| 环节 | 方案 |
|---|---|
| 文档存储 | Docker volume |
| OCR | 服务器本地或云端 API |
| AI 模型 | 服务器本地（如有 GPU）或云端 API |
| 检索 | Elasticsearch / Whoosh |
| 实体注册表 | 加密数据库存储 |

云端部署时，"本地"指用户自己的服务器，仍有数据主权。

### 11.3 混合部署

- 桌面端负责日常文档处理（导入、脱敏）
- 云端负责 AI 计算（大模型推理）
- 脱敏后的材料可安全同步到云端
- 原始材料保留在桌面端，不同步

## 十二、后端 API 重构

### 12.1 新 API 结构

```
/documents                         ← 合并原 /knowledge + /desensitize
  /files                           上传/列表/删除
  /files/{id}/parse                触发解析（指定引擎）
  /files/{id}/desensitize          触发脱敏（指定引擎+策略）
  /files/{id}/validate             AI 验证
  /files/{id}/content              获取内容（?version=original|desensitized）
  /files/{id}/status               获取流水线状态
  /desensitize-text                快速脱敏（不入库）
  /engine-config                   引擎配置 GET/PUT
  /engine-diagnostics              引擎诊断状态

/cases                             ← 案件中心
  /                                案件 CRUD
  /{id}                            案件详情（含仪表盘数据）
  /{id}/materials                  案件关联材料
  /{id}/entities                   案件实体注册表
  /{id}/entities/merge             合并别名
  /{id}/entities/check             一致性检查
  /{id}/timeline                   案件时间线
  /{id}/scan                       扫描外部文件夹

/documents/wiki                    ← 知识库（原 /wiki）
  /ingest                          从脱敏文档生成知识卡片
  /pages                           知识页面查询
  /pages/{path}                    读取知识页面
```

### 12.2 旧 API 兼容

旧 API 路径保留，内部转发到新 API：
- `/knowledge/*` → `/documents/*`
- `/desensitize/*` → `/documents/desensitize-text`
- `/wiki/*` → `/documents/wiki/*`
