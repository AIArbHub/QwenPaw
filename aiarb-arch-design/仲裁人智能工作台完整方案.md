## 一、现状全面诊断

### 1.1 整体架构问题："有零件无整车"

AIArb 拥有丰富的底层能力，但这些能力像散落的零件，没有组装成面向用户的完整产品：

| 已有能力 | 所在位置 | 当前状态 | 问题 |
|---|---|---|---|
| **多 Agent 编排** | `moot/orchestrator.py` | 可让多个 AI 角色按序发言 | 仅用于模拟庭审，不渗透到其他功能 |
| **Skill 系统** | `agents/skill_system/` | 有 PDF/docx/pptx/browser 等 20+ 内置技能 | 技能只在 Chat 对话中触发，不主动服务案件 |
| **MCP 协议** | `app/mcp/` | 支持 MCP 工具调用 | 未与仲裁业务关联 |
| **文档解析 3 层** | `parsers/router.py` | MinerU(云/本地) → Tesseract → MarkItDown | 能力强但入口分散，用户不知道用哪个 |
| **本地脱敏** | `knowledge/desensitize.py` | 正则脱敏 + LLM 补充脱敏 | 只有 Knowledge 页面能触发，仲裁模块无法用 |
| **LLM Wiki** | `wiki/engine.py` | 可从文档生成知识页、预测 QA | 独立页面，和 Knowledge/Cases 割裂 |
| **ReMe 记忆** | `agents/memory/reme_light_memory_manager.py` | 自动记忆、搜索、dream | 仅在 Chat 中生效，案件上下文不写入记忆 |
| **内置 Agent** | `builtins/arbitrator/`, `builtins/casemanager/` | 仲裁员 + 秘书 Agent 配置 | Profile 好但没融入业务流程 |
| **案件文件管理** | `moot/store.py` | 有文件上传/版本/可见性 | 仅限模拟仲裁案件，真实案件管理在 Cases 模块 |
| **本地大模型** | `local_models/` | llama.cpp 本地推理 | 可用于低配脱敏/OCR 后处理，未启用 |

### 1.2 仲裁业务区问题：6 个页面 5 个割裂

当前仲裁业务区有 6 个菜单项，用户需要在它们之间来回切换：

```
本地资料 (Knowledge)  ←→  模拟仲裁 (Moot)  ←→  文档智能 (Desensitize)
        ↑                                           ↓
案件卷宗 (Cases)  ←→  Wiki  ←→  记忆中心 (Memory)
```

**典型痛点场景**：用户想处理一个真实仲裁案件的文档：
1. 先去「案件卷宗」创建案件、关联文件夹
2. 去「本地资料」上传文档、等待解析
3. 去「文档智能」做脱敏
4. 回「本地资料」查看脱敏结果
5. 去「Wiki」手动编译知识页
6. 想 AI 辅助时，去「Chat」但发现 AI 不知道案件上下文
7. 想模拟庭审时，去「模拟仲裁」但发现和真实案件无关

**7 步操作跨 5 个页面**，这在 AI 时代是不可接受的。

### 1.3 模拟仲裁模块问题：自成一统

模拟仲裁（Moot）模块虽然实现了庭审风格和 AI 自动发言，但存在严重割裂：

- **与真实案件无关**：模拟仲裁案件和 Cases 模块的案件完全独立，不能"从真实案件一键生成模拟"
- **无文档支撑**：庭审中不能引用证据材料，AI 角色看不到案件文档
- **无知识库支撑**：AI 角色不知道仲裁规则、类案等知识
- **无记忆沉淀**：模拟结束后，AI 的发言、推理过程不进入知识库
- **评分不融入**：评分结果仅停留在当前案件，不形成能力画像

### 1.4 知识库问题：不像 Obsidian

当前 Knowledge 页面是传统的文件管理器：
- 上传 → 等待解析 → 查看列表 → 点击查看内容 → 手动脱敏 → 手动编译 Wiki
- 没有 Obsidian 的「点击即看、双向链接、图谱视图」
- 没有 LLM Wiki 的「喂进去就结构化」
- 搜索能力弱，只能按 tag/category/owner 筛选
- 文档之间无关联，无知识图谱

### 1.5 命名混乱问题

| 当前命名 | 问题 |
|---|---|
| `moot` (模块名) | 用户看不懂"Moot"是什么 |
| `Desensitize` / `DocForge` / `文档智能` | 三名并存 |
| `reme` / `ReMeLight` | 用户不知道这是什么 |
| `Tribunal` | 和 Moot 重复 |
| `Knowledge` vs `Wiki` vs `Cases` | 职责重叠 |

## 二、核心理念：从"系统"到"工作台"

### 2.1 设计哲学转变

```
旧理念：系统 → 功能 → 页面 → 操作
新理念：工作台 → 场景 → 上下文 → AI 辅助
```

**不是让用户在系统里操作，而是让 AI 在工作台里辅助用户。**

### 2.2 三条产品原则

1. **一个案件就是一个工作区** — 用户打开案件，一切上下文自动就位：文档、知识、AI 角色、脱敏状态、时间线
2. **AI 永远在线，不是工具而是伙伴** — 不是"点击按钮调用 AI"，而是"AI 在旁边看着你工作，随时提供建议"
3. **渐进式复杂度** — 新手看到的是简洁的引导流，专家看到的是强大的控制台

### 2.3 与现有产品的差异化

| 维度 | Obsidian/Notion | 通用 AI 助手 | AIArb 仲裁工作台 |
|---|---|---|---|
| 知识管理 | ✅ 双向链接、图谱 | ❌ 无 | ✅ 文档自动结构化 + Agent 记忆 |
| 案件管理 | ❌ 无 | ❌ 无 | ✅ 案件为中心的组织单元 |
| 文档智能 | ❌ 无 | 部分 | ✅ 本地 OCR + 脱敏 + 结构化 |
| AI 角色 | ❌ 无 | 通用 | ✅ 仲裁员/秘书/代理人专业角色 |
| 保密性 | 云端 | 云端 | ✅ 本地优先，渐进式云端 |
| 庭审模拟 | ❌ 无 | ❌ 无 | ✅ 风格驱动的 AI 庭审 |

### 4.3 三栏详细设计

#### 左栏：案件侧栏（Case Sidebar）

不再是一个平铺的菜单，而是一个**案件导航树**：

```
📋 概览
  ├── 案件信息（案号、当事人、仲裁机构）
  ├── 程序时间线（立案 → 组庭 → 开庭 → 裁决）
  └── 状态总览（文档 X/Y 就绪，脱敏 Z 项）

📁 材料中心
  ├── 申请人证据 (5)  [3 已脱敏]
  ├── 被申请人证据 (3) [1 已脱敏]
  ├── 合同文件 (2)
  ├── 鉴定报告 (1)
  └── + 添加材料

⚖️ 庭审
  ├── 真实庭审记录
  ├── 模拟庭审 (链接到 Moot)
  └── 庭审准备清单

📝 文书
  ├── 裁决书草稿
  ├── 程序决定书
  └── + 新建文书

📜 知识与记忆
  ├── 本案相关知识点 (自动关联)
  ├── 类案参考 (AI 推荐)
  └── 工作笔记
```

#### 中栏：主工作区（Tab 切换）

**Tab 1: 文档**（合并 Knowledge + Desensitize 的功能）

- **AI 分析**：点击「分析」按钮，AI 自动提取关键信息、识别争议点、建议证据关联
- **双版本对比**：点击文档展开原文/脱敏版对比，不需要跳到独立页面

- **记忆连通**：对话内容自动进入 ReMe 记忆，下次打开案件时 AI 还记得

class CaseLink(BaseModel):
    """案件与文档/知识的关联"""
    case_id: str
    doc_id: str = ""

    link_type: str = "evidence"  # evidence / reference / context

    case_summary: str = ""

            doc_text = await load_desensitized_doc(link.doc_id)
            evidence_texts.append(f"[证据{link.side}] {doc_text[:500]}")
    
    knowledge_texts = []
    for link in case_links:
        if link.link_type == "reference":
            wiki_content = await wiki.read_page(link.wiki_page_path)
            knowledge_texts.append(wiki_content[:500])
    
    full_prompt = (
        f"你正在参与模拟仲裁庭审...\n"
        f"案件证据材料：\n{chr(10).join(evidence_texts)}\n"
        f"相关知识：\n{chr(10).join(knowledge_texts)}\n"

## 八、渐进式本地化 OCR 与脱敏方案

### 8.1 问题分析

仲裁对保密性要求高，但用户设备配置差异大。需要渐进式方案：

| 配置等级 | CPU | RAM | GPU | 可用方案 |
|---|---|---|---|---|
| 低配 | i3/赛扬 | 4GB | 无 | Tesseract OCR + 正则脱敏 |
| 中配 | i5/i7 | 8-16GB | 无 | Tesseract + 正则 + 本地 LLM 脱敏 |
| 高配 | i7/i9 | 16GB+ | 有 | MinerU 本地 + 正则 + 本地 LLM |
| 云端 | 任意 | 任意 | 任意 | MinerU 云 + 正则 + 云 LLM |

### 8.2 渐进式 OCR 方案

```
用户上传文档
     ↓
检测文档类型
     ↓
┌─── 是否有文本层？(PDF) ───┐
│                           │
是                           否
│                           │
↓                           ↓
MarkItDown 直接提取          检测可用 OCR 引擎
(最快，无 OCR)                    ↓
                          ┌── 本地 MinerU？──┐
                          │                  │
                          是                  否
                          │                  │
                          ↓                  ↓
                          本地 MinerU         ┌── Tesseract？──┐
                          (高精度，离线)       │                │
                                              是                否
                                              │                │
                                              ↓                ↓
                                              Tesseract        提示用户
                                              (基础 OCR)       配置 OCR 引擎
```

**关键改进**：当前 `ParserRouter` 已经实现了这个逻辑！但用户不知道。改进方向：

1. **自动检测并提示**：首次使用时，自动检测可用引擎，告知用户
2. **智能降级**：OCR 失败时自动降级，不需要用户手动切换模式
3. **安装引导**：如果检测到低配环境且无 OCR，引导安装 Tesseract（轻量，无需 GPU）

### 8.3 渐进式脱敏方案

```
文档解析完成
     ↓
检测脱敏配置
     ↓
┌── 第 1 层：正则脱敏 ──────────────────────────┐
│  本地执行，零延迟，零云端                      │
│  覆盖：身份证、手机号、银行卡、地址、邮箱等     │
│  16 条规则（desensitize.py 中的 DEFAULT_RULES）│
└──────────────────────────────────────────────┘
     ↓
┌── 第 2 层：LLM 补充脱敏（可选）────────────────┐
│  方式 A：本地 LLM（llama.cpp，低配可用）        │
│  方式 B：云端 LLM（仅发送已部分脱敏的文本）     │
│  覆盖：零散人名、职务+年龄组合、地域标识等       │
└──────────────────────────────────────────────┘
     ↓
┌── 第 3 层：AI 验证（可选）─────────────────────┐
│  LLM 检查脱敏结果，确保无遗漏                   │
│  输出验证报告，标记可能遗漏的位置                │
└──────────────────────────────────────────────┘
     ↓
存储脱敏版 + 原始版（加密）
     ↓
AI 只接触脱敏版
```

**安全保证**：
- 云端 LLM 永远只接触已脱敏文本
- 原始版存储使用 Fernet 加密（已有能力）
- 用户可选择「仅本地」模式，完全不使用云端

### 8.4 技能复用

当前 `pdf` 技能可以处理 PDF，但只在 Chat 中触发。改为：

```python
# 技能可以注册为「文档处理器」，在文档上传时自动调用

    # 自动脱敏

```

## 十一、实施路线图

### Phase 1：UI 合并（1-2 周，低成本高感知）

**目标**：让用户感觉页面变少了，操作变简单了

1. **创建仲裁工作台页面** `/desk`
   - 合并 Moot + Cases 列表为统一案件列表
   - 案件详情页使用三栏布局
   - 复用现有 Moot 组件作为庭审 Tab
   - 复用现有 Cases 组件作为文档 Tab
   
2. **创建知识工作台页面** `/knowledge`
   - 合并 Knowledge + Wiki 列表
   - 知识详情页展示 Wiki 内容 + 文档关联
   - 添加拖入文档区

3. **简化文档引擎设置** `/engine`
   - 从 Desensitize 页面提取引擎状态部分
   - 合并解析引擎和脱敏引擎的配置

4. **菜单更新**
   - 仲裁业务区从 6 项减到 3 项
   - 旧路由重定向到新路由

### Phase 2：文档流水线自动化（2-3 周）

**目标**：拖入文档，自动完成全流程

1. **文档上传自动流水线**
   - 上传后自动解析 → 脱敏 → AI 分析 → 结构化
   - 流水线状态可视化（Pipeline 组件已有）
   
2. **技能复用**
   - 将 pdf/docx/pptx 技能注册为文档处理器
   - 文档上传时自动调用
   
3. **脱敏内联化**
   - 文档列表中直接显示脱敏状态
   - 一键脱敏，不需要跳转页面

### Phase 3：AI 上下文融合（2-3 周）

**目标**：AI 知道你在做什么，主动提供帮助

1. **案件上下文注入**
   - `CaseLink` 模型实现
   - AI 助手对话时自动注入案件上下文
   - 模拟庭审时自动注入文档和知识
   
2. **Copilot 面板**
   - 右栏 AI 助手组件
   - 上下文感知的对话
   - 主动提示功能
   
3. **ReMe 记忆融合**
   - 案件操作写入记忆
   - 知识搜索同时搜索记忆

### Phase 4：知识图谱与语义搜索（3-4 周）

**目标**：知识不仅存起来，还能被发现和关联

1. **双向链接**
   - Wiki 页面自动识别关联
   - 双向链接模型实现
   
2. **知识图谱视图**
   - 可视化知识网络
   - D3.js 或 vis.js 实现
   
3. **语义搜索**
   - 基于 ReMe 的语义搜索
   - 自然语言查询

### Phase 5：渐进式本地化（持续）

**目标**：低配设备也能用

1. **Tesseract 安装引导**
   - 检测到无 OCR 时，引导安装
   - Windows/Mac 安装包链接
   
2. **本地 LLM 脱敏**
   - 接入 `local_models/` 的 llama.cpp
   - 小模型（Qwen2.5-3B）做脱敏补充
   
3. **MinerU 本地部署引导**
   - 检测到高配设备时，引导安装本地 MinerU
   - 自动启动和管理
