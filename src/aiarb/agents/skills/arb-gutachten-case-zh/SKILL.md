# 仲裁鉴定式案例研习超级工作流

本 skill 是一份面向仲裁实务的、可移植的鉴定式案例分析工作流。它将**"请求权基础方法（Anspruchsgrundlage）"**与**"鉴定式写作（Gutachten）"**两套方法论结合**仲裁程序法特点**编排为四段工作流，内置解题大纲生成引擎（outline-engine）自主完成请求权基础鉴定式分析。


## 一、什么时候用本 skill

用户提交仲裁案件材料并需要按学术/实务规范输出案例分析报告时——典型场景：

- 仲裁代理人 / 律师为复杂仲裁案件做"内部全要件检视"作为后续仲裁申请书/答辩状/代理意见的底稿；
- 法务人员评估仲裁风险、制定仲裁策略；
- 法律研究者撰写仲裁案例研究文章；
- 用户希望系统理解一个真实仲裁案件的全部请求权 / 抗辩 / 程序问题。

**不适用**：
- 仲裁申请书 / 答辩状 / 代理意见等具体仲裁文书（请使用 `arb_document_draft-zh`）；
- 纯诉讼场景（请使用原版 gutachten-civil-case）；
- 快速合规咨询（请使用 `legal_research-zh`）。

## 二、核心方法论

### 2.1 与原版（民事鉴定式）的关键差异

| 维度 | 原版 gutachten-civil-case | 本版 arb-gutachten-case |
|------|--------------------------|------------------------|
| 程序框架 | 民事诉讼法 | 仲裁法 + 仲裁规则 |
| 管辖权审查 | 法院主管与管辖 | **仲裁协议效力 + 仲裁委员会管辖** |
| 当事人称谓 | 原告/被告 | **申请人/被申请人** |
| 文书称谓 | 起诉状/判决书 | **仲裁申请书/裁决书** |
| 救济途径 | 上诉/再审 | **撤销裁决/不予执行/执行** |
| 程序特性 | 两审终审 | **一裁终局** |
| 证据规则 | 民诉证据规定 | **仲裁证据规则（更灵活）** |

### 2.2 方法论文件清单

| 模块 | 文件 | 内容 |
|------|------|------|
| 内在结构 | methodology/inner-structure.md | 三层（产生/未消灭/可行使）四步、否认 vs 抗辩、抗辩—再抗辩链 |
| 外在结构 | methodology/examination-sequence.md | **六级检索**（仲裁协议效力→双方关系→仲裁请求→规范类别→具体规范→检视程式）、18 类规范基础 |
| 写作风格 | methodology/gutachten-writing-rules.md | 鉴定式/裁判式句式、**仲裁术语统一**、法条引用规则、脚注规范 |

| **仲裁程序** | **methodology/arbitration-procedure.md** | **【新增】仲裁协议效力、仲裁管辖权、仲裁程序事项、裁决执行** |

### 2.3 仲裁程序前置审查（新增模块）

在进入实体请求权分析前，必须先完成以下仲裁程序性审查：

#### （1）仲裁协议效力审查
- 仲裁协议形式（书面要求）
- 仲裁事项范围
- 仲裁机构约定（明确性要求）
- 当事人行为能力
- 意思表示真实
- 特殊情形：仲裁协议无效、失效、无法实施

#### （2）仲裁管辖权审查
- 仲裁委员会的管辖权限
- 仲裁地法律适用
- 多份合同/多组合同下的仲裁协议处理

#### （3）仲裁程序合法性（事后审查）
- 仲裁庭组成合法
- 程序正当（通知、陈述机会）
- 超裁/漏裁审查

## 三、工作流（四段）

```
[首次使用] 0-cold-start-interview → 写入 .user-config.md（能力槽注册 + 偏好设置）

每次会话（严格遵守"事实—设问—规范"阀门，内含于 W1/W2）：

┌─────────────────── W1（事实+设问层） ───────────────────┐
│  1-case-intake    （PDF/Word/图片 → 中性事实笔记 + 设问逐字 + 法律关系对）│
└────────────────────────────────────────────────────────────┘

┌─────────────────── W2（规范层起点 · 两闸独立确认） ───────────────────┐
│  2a-preselection  （【仲裁程序前置审查】+ 解题大纲生成引擎 + 法律数据库双层校验 → 候选清单 → 闸一确认）│
│  2b-outline       （已确认清单展开为三阶段要件大纲 → 闸二确认）               │
└────────────────────────────────────────────────────────────────────────┘

┌─────────────────── W3（并行写作） ───────────────────┐
│  3-drafting       （≥2 法律关系对多 subagent 并行；即时校验；法律解释贯穿）│
└──────────────────────────────────────────────────────┘

┌─────────────────── W4（差异核验+输出） ───────────────────┐
│  4-verification-and-output （增量法条校验+覆盖忠实+格式扫描 → 一次性修订 → 输出）│
└────────────────────────────────────────────────────────────┘
```

## 四、能力槽体系（Capability Slots）

本 skill 不绑定任何特定工具产品。所有外部依赖均抽象为"能力槽"，首次使用时由冷启动访谈引导用户配置。

### 4.1 标准能力槽

| 编号 | 能力槽名称 | 槽位标识符 | 功能描述 | 是否必须 |
|---|---|---|---|---|
| S1 | 法律数据库检索 | `[SLOT-LEGAL-DB]` | 法条检索、条文原文获取、现行有效性校验、司法解释检索 | 必须（可降级） |
| S2 | 文档解析 | `[SLOT-DOC-PARSE]` | PDF / Word / 图片 → Markdown 转换 | 可选 |
| S3 | 全网搜索 | `[SLOT-WEB-SEARCH]` | 学术论文、实务文章、法律资讯检索 | 可选 |
| S4 | Word 输出 | `[SLOT-WORD-OUTPUT]` | Markdown → Word (.docx) 格式转换与输出 | 可选 |
| S5 | **仲裁裁决检索** | **`[SLOT-ARB-SEARCH]`** | **仲裁裁决书检索、仲裁案例库查询** | **可选（推荐）** |
| S6 | 学术论文检索 | `[SLOT-PAPER-SEARCH]` | 学术论文全文获取 | 可选 |

## 五、关键约束（三层）

### 铁律层（违反即报告失败）

1. **仲裁协议效力前置审查铁律**：本 skill 在进行任何实体请求权分析前，必须先完成仲裁协议效力的形式和实质审查。如仲裁协议可能无效，须在报告中单独列明并分析其对案件的影响。

2. **法条校验铁律**：同原版，所有法条号须经 `[SLOT-LEGAL-DB]` 校验。

3. **方案先确认再开工 · 两闸独立**：同原版。

4. **阀门约束**：同原版。

### 规范层（标准遵循）

5. **检视程式骨架**：报告正文须严格遵循三层四步内在结构。

6. **完整自含的脚注（真实来源原则）**：同原版。

7. **法律解释方法贯穿全程**：增加**仲裁法解释特殊性**考量。

8. **格式真相源**：`examples/canonical-report-template.md` 为唯一权威基准。

9. **论证深度比例原则（proportionality）**：同原版。

10. **法条全文展开**：每个被引用的法条第一次出现必须完整展示原文。

11. **客观第三人称**：避免主观色彩；当事人称谓统一使用**申请人/被申请人**。

12. **三维核验闭环**：同原版。

### 弹性层

13. **报告字数区间**：默认 ≤ 30,000 字。

14. **反对说展开深度**：默认对核心争议要件展开正反论证。

15. **仲裁规则选择**：用户可在冷启动时指定适用的仲裁规则（CIETAC/SHIAC/BJIAC/SCIA等），不同规则的程序差异将在报告中体现。

## 六、输出格式

要点摘要：

- A4 / 上下 2.54cm / 左 3.17cm / 右 3.07cm / 行距 1.25 倍；
- 正文宋体小四（12pt）；
- 段首全角空格 ×2；
- 来源标识符四种：`[文献]` / [案例] / [联网] / `[KB:]`；
- 必有目录页 + 大纲 + 正文双 H2 外壳层；
- **部分层条件化**：当事人对数 ≥ 2 加 `# 第X部分`；
- 总字数 ≤ 30,000 字（含脚注）。

## 八、执行入口

收到触发请求时按下列顺序处理：

1. 检测 `.user-config.md` 是否存在：
   - 不存在 → 执行 `0-cold-start-interview`，访谈完成后保存配置；
   - 存在 → 跳过冷启动，进入第 2 步。

2. 解析用户输入：
   - 用户已提交案件材料 → 进入 `1-case-intake`；
   - 用户仅询问方法论 → 直接读取相应方法论文件回应。

3. 按工作流逐段推进：W1 → W2 闸一（**含仲裁协议审查**）→ W2 闸二 → W3 → W4。

4. 每段进入下一段前必须用户独立确认；W2 两闸禁合并。
